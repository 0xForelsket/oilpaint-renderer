# L2 report: ScenePlan v1, JSON Schema, scene compiler, TS DSL

Milestone L2 of `docs/plans/LIBRARY_PLAN.md` (v4), 2026-09-30.

Machine: Windows 11 laptop, Intel Core Ultra 7 258V, 32 GB, rustc 1.91.1 MSVC, Node 24.11.1, Python 3.12.
Everything below is *measured* unless marked *projected*. Timings are single-thread, pinned to the performance
cores.

## Summary

- **Acceptance: met.**
  - Storm Light's guide sheets are generated from TypeScript: `scenes/storm_v3.ts` → ScenePlan JSON → the Rust
    compiler as WASM → `docs/reports/L2/storm_guides_sheet_ts.png`.
  - Compile time is measured (below).
- **ScenePlan v1 is frozen** (`spec/SCENEPLAN_V1.md`). There is one source of truth: the Rust types generate the
  JSON Schema, and the schema generates the TypeScript types. Tests fail if either generated file is stale.
- **Validation is agent-grade.**
  - Every error is `{code, path, got, expected, fix}`, with a JSON Pointer.
  - An unknown key gets a did-you-mean fix, and v1 or snake_case names get the right key.
  - Sizes that look like pixels get a `UNITS` error with the conversion.
  - The same Rust validator runs in the CLI, in WASM and in the TS API.
- **The compiler reproduces v1's guides closely.** It keeps v1's formulas and defaults; the rasterisation and noise
  are the engine's own. On Storm Light at 600 px:
  - target: mean difference 2.5/255, PSNR 33 dB;
  - region map: 99.7% agreement;
  - light map: within 0.003;
  - flows: noise-free flows within 1°. Noisy flows differ exactly as much as v1 differs from itself with another
    seed.
- **Determinism holds on 7 hosts.** The six guide planes and the validation report are byte-identical on native
  Windows, Node, Chromium, Firefox, WebKit, Chrome and Edge, and they are now in the goldens.
- **Compiling is 3–6x faster than v1.** Storm Light guides at 600 px, medians of one interleaved round:
  - v1 (Python): 4.1 s;
  - native: 0.69 s;
  - WASM in Chromium: 1.16 s;
  - WASM in Node: 1.39 s.
- **The TS package has no runtime dependencies.** Node 24 runs the TypeScript directly: there is no build step until
  packaging (L4/L6).

## ScenePlan v1 and validation

- **The spec.** `spec/SCENEPLAN_V1.md` defines the format and the compiler's semantics:
  - the raster and the noise;
  - every shape, target op, flow and light, with its formula;
  - the region rules, the map defaults and the sampled fields.
- **Schema.** The schema is draft-07, since most editors and generators read it. Its descriptions carry each key's
  unit and default.
- **Storm Light port.** `scenes/storm_v3.ts` ports `storm_v3.py` call for call: 53 target ops, 20 regions,
  19 styles and 15 layers. It builds its spec in 14 ms.

Example (a style width written in pixels):

```json
{"code":"UNITS","path":"/styles/sky/width/0","got":"25","expected":"(0, 0.5] cw",
 "message":"width[0] is too large for canvas widths",
 "fix":"coordinates and sizes are in canvas widths (cw): divide pixels by the canvas width in pixels: 25 px on a 600 px plan is 0.0417 cw"}
```

**Validation fixes by kind of error:**
- a typo (`widht`): `did you mean "width"?`;
- snake_case (`stop_at_edge`): `keys are camelCase: use "stopAtEdge"`;
- a v1 name (`T`): `v1's T is "errorThreshold" in a ScenePlan`;
- a colour typo (`cobalt_bleu`) or a region typo (`skye`): a did-you-mean fix.

**Coverage.** Schema errors stop at the first (a serde limit). Semantic errors are all reported.

**The validator found a bug of its own.** It first read `jitter` as a `[min, max]` range, and Storm Light's
`[6, 4]` failed. `jitter` is `[L, a/b]`; fixed.

## The compiler against v1

`tools/compare_guides.py` runs v1's `SceneBuilder.guides` on `storm_v3.py` and compares it with the engine's
planes (`oil guides --npy`). Storm Light at 600 px:

| Plane | Engine against v1 |
|---|---|
| target | mean 2.46/255, p99 22.7/255, max 74.5/255, PSNR 33.3 dB |
| region map | 99.68% of pixels agree; IoU ≥ 0.97 for the large regions (sky, storm, glow, sea, rock, crest) |
| soft masks | mean difference ≤ 0.0015 per region |
| light | mean 3e-5, max 0.0027 |
| flow | median 7.6° (mean 10.5°); flows with little or no noise (ground, rain, tower, bands, beam, gallery, roof) 0.4–1.1° median |

**Where the target and flows differ is noise realisation.**
- v1 drew its noise lattices from numpy's PCG64 stream. The engine hashes (seed, octave, i, j), so the field is
  the same at every size and on every host.
- The fields are statistically equivalent. The engine-vs-v1 angle differences match v1-vs-v1 with a different seed:

| Region flow | v1 vs v1 (other seed): median / p90 | Engine vs v1: median / p90 |
|---|---|---|
| sky (sweep) | 12.4° / 32.0° | 10.1° / 31.6° |
| rock (contour) | 15.4° / 35.9° | 14.5° / 36.5° |
| halo (radial) | 19.8° / 44.2° | 18.9° / 45.1° |
| sea_near (waves) | 5.1° / 14.0° | 4.9° / 13.7° |

- The largest target differences are the edges of blobs with noise 0.5–0.8 (the storm clouds, the squall bank)
  and the sea's wave phase stripes.

**Small polygons differ by rasterisation, and the engine's is the exact one.**
- v1's `cv2.fillPoly` rounds vertices to whole pixels and fills its outline inclusively, so its polygons come out
  about one pixel wider.
- The gallery (0.104 x 0.013 cw) is 487 px exactly at 600 px; the engine fills 496 and v1 567.
- Hence IoU 0.87–0.95 for the gallery, roof, foot, lantern and bands, and for the halo, which gains the pixels
  those lose. Foam, a band around the rock's outline, is at 0.93; the rest are ≥ 0.96.

**Other deliberate differences** (all in the spec):
- the depth of `waves` runs to the canvas bottom, not the last pixel row (so it does not depend on resolution);
- `contour` uses an exact EDT, where v1 used OpenCV's 5x5 approximation;
- masks use the engine's blur, which downsamples above 8 px, where v1 used a full Gaussian.

## Determinism

`ci/xhost` gained seven cases:
- `scene.storm_v3@600.{target, regionId, masks, flow, regionFlows, light}` compile the committed example ScenePlan;
- `scene.validate.codes` validates a plan with four planted errors (codes, paths and values, in order).

**Result:** all seven are identical on native Windows, Node 24, Chromium 145, Firefox 146, WebKit 26, Chrome 154
and Edge 154. The existing 22 cases still match `golden/2.0.0-dev.2.json`, and the 7 new ones were added to it (29
cases, 7 hosts).

- **No engine bump.** L2 adds outputs and changes none, so the engine version stays `2.0.0-dev.2`.
- **Validation messages are not hashed.** Messages and fixes are free text that may improve without a bump, so the
  golden hashes codes and paths only.

|---|---|---|---|
| v1 Python (`SceneBuilder.guides`) | 4.06 s | 3.43–5.70 s | 1x |
| engine, native (`oil guides`) | **0.69 s** | 0.64–1.00 s | 5.9x |
| engine, WASM in Chromium 145 | **1.16 s** | 1.13–1.70 s | 3.5x |
| engine, WASM in Node 24 | **1.39 s** | 1.30–2.01 s | 2.9x |

**Other rounds** (pinned, not interleaved):
- 600 px, the steadiest round: v1 3.27–3.43 s, native 0.61–0.62 s, Node 1.19–1.24 s, Chromium 1.03–1.15 s.
- 1200 px: v1 17–27 s, native 2.8–5.4 s, Node 5.8–10.2 s, Chromium 4.4–5.0 s.
- WebKit and Firefox (from the cross-host run, unpinned, 600 px): WebKit 1.3–2.0 s. Playwright's Firefox runs WASM
  on its baseline tier only (6.4–10.1 s), so it is not a measure of Firefox; the same was true in L1.

**Why there are several rounds.** The same native command took 0.61 s in one round and 1.10 s (median) in another
an hour later. This laptop's power management moves absolute times by up to 2x, even pinned, so only numbers from
the same round are compared.

**Where the native time goes** (600 px, pinned, medians):
- the flows take 48%: 20 region flows over the whole canvas plus the structure tensor;
- the target takes 28%;
- regions and soft masks take 20%;
- light takes 4%.

**Other costs:**
- The TS DSL builds the spec in 14 ms, including the module import.
- `oil guides` writes its previews (five PNGs) in 0.26 s.

**WASM size:** `oil.wasm` is 1.30 MB, 373 KB gzipped and 264 KB brotli. It has not been through wasm-opt. It
includes Ochrell's tables and the schema generator.

## Decisions I took (reversible, flagged for the record)

1. **Hashed-lattice noise instead of v1's PCG64 lattices.** It is the same at every resolution and on every host,
   and statistically equivalent to v1's (table above).
2. **Pixel-centre polygon fill and an exact EDT.** Areas are exact; thin features are about a pixel narrower than in
   v1.
3. **Curve placement with no `curve` map** follows every region's boundary. v1 crashed there.
4. **JSON Schema draft-07,** not 2020-12. json-schema-to-typescript and most editors read draft-07 tuples.
5. **TypeScript without a build step** (Node 24 type stripping, erasable syntax only). The published build
   (tsc emit) comes with packaging.
6. **Error messages and fixes are free text** and not versioned. Codes and paths are stable (`spec/ERRORS.md`).
7. **A minimal `oil-wasm` now** (validate, schema, guides, planes, previews) rather than in L4, because the TS
   acceptance needed it.

## What failed or is open

**Bugs found and fixed in L2:**
- **WASM memory view.** `engine.ts` built a view of the WASM memory before calling `oil_input`, which can grow the
  memory and detach that buffer. It worked in Node by luck; a Chromium timing script hit it. A test now forces the
  growth.
- **SHA-256 padding.** The package's own SHA-256 padded one block too many when the length + 9 was a multiple of 64.
  A test against `node:crypto` at block boundaries caught it before any use.
- **The `jitter` rule** (above).
- **Hosts list in the golden.** Writing the golden from a 5-browser run dropped Chrome and Edge from its hosts list.
  I re-ran them, so the golden again lists all 7 hosts.

**Open:**
- **Flow memory at large widths.** Every authored flow is kept whole-canvas: 20 × 8 B/px, 72 MB at 600 px and
  *projected* 1.15 GB at 2400 px.
  - The planner plans at 600 px, so this is fine for L3.
  - L3 could instead evaluate the analytic flows at stroke points (they are functions of (x, y)) and drop the
    region-flow rasters. That would also remove half of the compile time.
- **To come with the planner (L3):**
  - the `strictEngine` option;
  - the `NON_PORTABLE_PLAN` warning;
  - boundary extraction for curve placement.
- **To come with L5:** `REGION_NO_FLOW` and the other planning warnings.
- **To come in L9:** the `facets` flow.
- **WASM size** (1.3 MB raw) is for L4's budget: embed the committed schema instead of generating it, and run
  wasm-opt.
- **Firefox timing** needs a stock Firefox, not Playwright's build (as in L1).
